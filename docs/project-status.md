# NUSGo Project Status

This document records the shared implementation status and near-term engineering direction. Stable domain and product vocabulary belongs in the root `CONTEXT.md`; agent behavior belongs in `AGENTS.md`.

## Stack

- npm workspaces: `frontend`, `backend`, and `shared`. `shared` owns HTTP contracts and pure canonical-data validation; `backend` provides the persistent Express API foundation.
- MapLibre GL JS for map rendering
- React 19, TypeScript, and Vite in `frontend`; static JSON data in `frontend/public/data`.
- Base UI Drawer for mobile sheet gestures and snap points, styled with the project's CSS tokens.
- Application code and types under `frontend/src`.

The accepted route architecture uses a self-hosted Valhalla pedestrian service behind a server-side boundary and a pure planner that composes walking connections with the canonical bus network. OSRM and other routing engines remain replaceable alternatives behind that boundary. Other potential future tools include `@turf/turf` for spatial calculations, `ical.js` for calendar import, and PostgreSQL/PostGIS behind a future API.

## Current implementation

- Waypoint data foundation: the frontend defines the shared Waypoint core and validated PersonalWaypoint model, with collections capped at 500 records. Reads retain valid records and report the count and validation issues for rejected records; malformed JSON and unsupported envelope versions stay available for explicit recovery. Versioned browser storage keys use `nusgo:<collection>:v<version>` (matching `nusgo:favorite-stops:v1`), and the serialized envelope also carries its version. Revision checks detect changes observed before a write, but localStorage cannot make cross-tab read/compare/write atomic. Personal records stay in this browser profile; add, manage, and Journey workflows remain follow-up work.
- Express owns process health, readiness, Journey planning, NUS shuttle arrivals and service windows, LTA public-bus arrivals, and the single-process 33-stop shuttle snapshot poller. It applies exact-origin CORS and bounded JSON parsing, validates canonical inputs at startup, keeps provider credentials and VALHALLA_BASE_URL in backend configuration, and stops upstream work during shutdown. The API has a short-lived per-client request budget, with a stricter Journey budget and a cap on concurrent Journey calculations; these controls are process-local. Vite serves the browser and its development `/api` proxy forwards requests to Express. Separately served frontends use an explicit VITE_API_ORIGIN; hosted builds require HTTPS, while the local rehearsal uses loopback Express and a separate output directory. API paths are independent of the static asset base. The root development command starts Express, Vite, and local Valhalla with shutdown cleanup, and the processes can also run independently.

The independent local run procedure, backend data files, data-version matching, and generated timing/walking-graph lifecycle are documented in [local services](local-services.md).

- A local Express container rehearsal is available through `backend/Dockerfile` and `docker-compose.rehearsal.yml`, with runtime-only provider credentials, packaged canonical/provider data, and unpublished private Valhalla. Live NUS and real-key LTA arrivals, Stops/Plan, Valhalla failure/recovery, CORS, restart/readiness, shutdown, and loopback/private-service port checks were exercised locally on 22 October 2026. Focused existing tests cover partial and total snapshot failures plus stale/expired snapshot freshness; no live provider outage was injected, and the Docker bridge does not guarantee API-exclusive access. Measurements and remaining #236/#102 verification are recorded in [local services](local-services.md#local-rehearsal-evidence--22-october-2026). Production ingress remains unverified; the composition uses development settings and is not a hosted deployment recipe.

- The Pathfinding engine lives in backend/src/pathfinding/. find-paths.ts coordinates endpoint resolution, walking connection selection, pure bounded search, bus-wait policy, and complete geometry. walking/ owns the directed stop-graph provider and Valhalla client; search/ owns indexing, enumeration, ranking, and budget control. POST /api/journeys accepts endpoint references or a frozen Current location coordinate and resolves canonical data on the server. The frontend sends endpoint identities only and receives complete scored Paths with geometry. The app session continues to own request identity and cancellation, Plan owns the four-option display policy, and MapLibre owns Path rendering.
- Pathfinding compares direct walking, one-bus, and one-transfer candidates. Venue endpoints contribute up to five reachable directed walking connectors selected by estimated duration. A selected origin stop stays fixed for boarding; a selected destination stop remains an exact zero-walk endpoint and may also use up to five directed final walks from other stops. A transfer walks to a different route, and a Path cannot revisit a stop or planning state. Scoring divides walking time by 0.8, leaves the first bus wait and ride unchanged, and divides each later bus leg by 0.9. Search returns up to three distinct bus-inclusive Paths plus the best walking-only Path. Candidates that are not worth showing are pruned by the shared policy in `shared/src/routing/candidate-policy.ts` before the top three are chosen: a bus Path whose adjusted duration is more than 2x the walking Path's is dropped, and a two-boarding Path is dropped unless it saves at least 180 seconds of adjusted duration over the best walking or single-boarding Path. Plan applies the same policy again before display. Plan separately displays up to three bus Paths and one walking Path; walking leads only when its adjusted duration is strictly below 80% of the fastest bus Path, otherwise it follows the bus options. Walking legs require complete Valhalla geometry, and the map renders each candidate while emphasizing the selected Path.
- Walking connection lookup reuses exact directed edges from the validated graph for the 33 canonical bus stops and asks Valhalla only for endpoint matrix cells not covered by those edges; when both are needed, origin-row and destination-column queries run in parallel. Search allows 350 ms and 10,000 expanded paths, checks cancellation, and yields between batches. Timing records, walking adjacency, and per-route stop projections are indexed or cached. Incomplete walking geometry discards only that candidate so the next ranked option can fill its category quota; if geometry completion exhausts its 350 ms budget, complete best-so-far candidates are returned as bounded, while no complete candidates produce a `planning_timeout` response. An `exact` result exhausts the supported candidate set; it does not establish a global optimum outside the selected connectors or beyond one transfer. Budget-limited output contains complete best-so-far candidates and is marked `bounded`.

## Current limitations

- `frontend/public/data/bus-routes.json` is the original route-name source; the app now consumes the normalized `shuttle-network.json` model.
- The checked-in model contains reviewed ordered stop IDs and bundled road-following GeoJSON route geometry; targeted release smoke evidence exists at 1280 × 720, while exact release/mobile viewports and failure injection still need manual verification.
- Accurate transit behavior depends on the checked-in network, geometry, and verification manifest remaining in sync; CI validates that integrity gate.
- The accepted Pathfinding architecture is documented in [ADR 0002](adr/0002-nus-route-recommendation-architecture.md) and [ADR 0003](adr/0003-three-stop-single-shuttle-recommendation.md), with the timing policy in [bus timing policy](shuttle-timing.md). The backend runs the Pathfinding engine and Valhalla adapter; deployment still needs a configured self-hosted Valhalla endpoint for usable walking results. Regenerate the checked-in walking stop graph when the canonical stop model, walking profile, or routing data changes. Bus ride estimates, live waits, service-window checks, and live-data failure distinctions are implemented; live data still depends on server-side NUS credentials. A valid no-bus response removes bus options, while provider failures surface as planning errors. Bounded search presents a complete valid Path as recommended without claiming a global optimum.
- NUSMods is useful for venue/stop associations and bus-arrival integration, but its current NextBus client does not provide route geometry. Live-arrival reliability also needs separate verification.
- The OpenFreeMap basemap is suitable for the prototype. NUS-specific paths, entrances, covered walkways, and indoor connections may require custom GeoJSON or another licensed data source.
- Location tracking depends on browser permission and device accuracy. It does not replace chosen trip endpoints, replan journeys, or continue after the app closes.
